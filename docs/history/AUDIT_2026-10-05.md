Fresh, full re-audit of the backend (`server/mileage-ingest`,
`server/mileage-viewer`, compose, Dockerfiles, runbook) and the Stage 4
firmware (`firmware/04_trip_logger/04_trip_logger.ino`). Every file was read
end to end rather than working from the previous finding list.

Follows `AUDIT_2026-08-04.md` (no code has changed since, apart from B2).
**No code was changed by this audit.** Fixes landed afterwards on the same
branch; see *Fix status* and *Bench results* at the end.

## Method

- **Backend:** suspect paths run against both apps through the Flask test
  client (Flask 3.0.3 / openpyxl 3.1.5 / tzdata 2026.3, the pinned set), with
  real SQLite and a real openpyxl round-trip. Docker Compose v5.3.1 used to
  check `env_file` handling.
- **Firmware:** compiled with arduino-cli against **ESP32 core 3.3.11**,
  XPowersLib 0.3.3 and TinyGPSPlus 1.0.3 (`esp32:esp32:esp32`,
  `PartitionScheme=default`). Library behaviour was checked against the
  installed library source rather than assumed (TinyGPSPlus sentence commits,
  HTTPClient stream upload, XPowersLib init).
- Items marked **(hardware)** cannot be settled without the board and are
  folded into the shakedown checklist at the end.

## Headline

1. **Firmware compiles cleanly on core 3.3.11**: 1,030,628 B (78%) program,
   56,544 B (17%) globals. The June "needs re-compiling" item is closed.
2. **Every August finding except B2 is still open**, and all four backend
   repros (B1, B3, B4, B5) still reproduce.
3. **F1 is worse than reported.** The README's partition scheme gives 1.375 MB,
   not 2.38 MB. That fills the flash in **about 43 minutes of driving**.
4. **New: the mileage number the server reports includes GPS jitter while
   the car is stopped** (N1), and **drops the distance across every GPS gap**
   (N2). This is the number that goes on the tax record. The raw GPX is kept
   unchanged, so both can be fixed later and every summary recomputed.

### F1 revised numbers

The README (`firmware/README.md:106`) and top-level README say to use
**"Default 4MB with spiffs"**. On core 3.3.11 that partition is `0x160000`
= **1.375 MB** (`tools/partitions/default.csv`), not the brief's 2.38 MB:

| Rate | Points that fit (281 B each) | Driving time to full |
|---|---|---|
| 2 Hz (today, F2) | 5,130 | **~43 min** |
| 1 Hz (after F2) | 5,130 | ~1.4 h |
| 1 Hz, ~110 B/pt, 2.38 MB custom partition | ~22,700 | ~6.3 h |

LittleFS metadata overhead makes the real numbers somewhat lower. The three
docs also disagree on the partition. The sketch header (`:31`) says
"No OTA (2MB APP/2MB SPIFFS)", the README says Default, and the brief says a
custom CSV. **Pick one (the brief's custom 2.38 MB layout) and make all three
say it.**

**Refinement to the August F1 decision:** don't drop `hdop` when slimming the
format. It's the only per-point quality signal, and without it the server
can't filter multipath fixes (see N1). `<hdop>1.2</hdop>` costs ~16 B. Drop
`sat`, `course` and `ele` instead.

# Part 2 — New findings

## High

### N1. Stationary GPS jitter is counted in the reported mileage

The firmware writes every fix in ACTIVE **and** COOLDOWN regardless of speed.
That includes the 3-minute end-of-trip cooldown, plus every red light (≤2 mph
drops ACTIVE into COOLDOWN, and points keep being written). The ingest server
then sums haversine over every consecutive pair in a segment
(`mileage-ingest/app.py:275-290`) with no speed or quality gate.

The June review's fix #4 ("jitter distance gate") only gates the
**device-side** `gTripMeters` (`:404-407`). That counter is used only for the
micro-trip discard decision and is never uploaded. **The number on the tax
record still includes the jitter.**

Reproduced: a synthetic 3-minute stationary cooldown with 0.3 m of random
wander per fix adds **64 m** on the server. The real magnitude depends on
sky view and the receiver's filtering, from tens to hundreds of metres per
stop, so it has to be measured on the shakedown. The direction doesn't
depend on that: it **overstates** business miles, which is the unsafe
direction for an IRS record.

**Fix (server, where the number is computed):** count a segment's distance
only when the point's reported `speed` is above ~2 mph (the GPX already
carries it), and skip points with `hdop` above ~5 once that's in the format.
Optionally trim the trailing stationary tail so `end_time` and duration stop
including the 3-minute cooldown (see N8). On the device, also configure the
M8N's **automotive dynamic model** (UBX-CFG-NAV5 `dynModel=4`) in the same
UBX block F2 needs. That cuts jitter at the source.

Because the raw GPX is stored byte for byte, a small "re-summarize all trips"
script can apply this retroactively. **It doesn't block the road test. It does
block trusting the totals at tax time.**

## Medium

### N2. Distance across a GPS gap is dropped entirely

A gap over 5 s (`SEG_GAP_MS`) starts a new `<trkseg>`, and the server counts
**zero** distance between segments. The ingest docstring (`:33-35`) justifies
this as "bridging it would invent miles". That's backwards: the straight line
between the last fix before a gap and the first fix after it is the
**shortest** path, so it's a lower bound on what was actually driven.

Reproduced: 3 km driven with a 1 km tunnel gap → server reports **1,997 m**.
Every tunnel, parking structure and urban canyon loses real deductible miles.

**Fix:** add the straight-line distance across a segment break, optionally
capped by `gap_seconds × last_speed`. That keeps it conservative and still
lower-bounded.

### N3. The GPS is probably not powered off in deep sleep, and has no backup power (hardware)

Stages 2–3 only ever *enabled* ALDO4 and saw the GPS work. That proves the GPS
gets power. It doesn't prove ALDO4 is what supplies it. The Stage 4 brief notes
the Meshtastic-confirmed V1.2 mapping is **ALDO3 = GPS**, and LilyGO's
T-Beam V1.2/AXP2101 example code uses ALDO3 for the GNSS and also enables
`VBACKUP` (the GNSS RTC/backup supply). If ALDO3 comes up on by default,
then:

- `deepSleepForVbus()` turns off only ALDO4 (`:573`), so the GPS keeps drawing
  ~25–30 mA while parked. An 18650 would be flat in a few days.
- With no `VBACKUP`, the M8N loses ephemeris and time every time it's powered
  down, so **every drive starts cold**. Positions before the first fix aren't
  buffered (the device has none to buffer), so roughly the first 30+ s of
  every trip from home is never logged.

**Test (two minutes on the bench):** in a scratch sketch, enable ALDO4 only
with ALDO3 explicitly disabled, then the reverse, and see which one stops the
NMEA. Then measure sleep current. If ALDO3 is the rail, switch to it, and
enable button-battery charge (`setButtonBatteryChargeVoltage(3300)`,
`enableButtonBatteryCharge()`, both present in XPowersLib 0.3.3).

### N4. The battery charges with no temperature protection (safety)

XPowersLib's `initImpl()` calls `disableTSPinMeasure()` by default
(`XPowersAXP2101.tpp:3087`). That's correct for a board with no thermistor,
but it means the AXP2101 charges the 18650 at any battery temperature. Li-ion
should only be charged between 0 and 45 °C, and a parked car's cabin regularly
exceeds 60 °C in summer. The sketch never sets the charge current or
target voltage either.

**Fix:** read the PMU die temperature (`getTemperature()`, available) and
disable charging above ~45 °C. Also consider a lower charge current and a
4.1 V target, which reduces heat stress and extends cell life in a car. Mount
the enclosure out of direct sun. If this matters to you, a LiFePO4 cell is the
more heat-tolerant chemistry.

### N5. The export is missing things a mileage log needs

What the IRS expects is general recordkeeping guidance, not tax advice;
confirm the details with your preparer.

- **No place/destination.** IRS guidance on adequate records centres on date,
  miles and business purpose, and logs conventionally record destination
  too. The export has no place field, only the free-text note, and the
  start/end coordinates exist in the GPX but aren't exported. **Fix:** export
  start and end lat/lon at minimum. A "destination" field next to the note is
  the better answer.
- **No "commuting" category.** Schedule C Part IV line 44 (and Form 4562
  Part V) splits miles into business, **commuting** and other. The categories
  are `business`, `personal` and `other` (`mileage-viewer/app.py:145`).
- **No year filter and no totals.** The export is every trip ever, with no
  business-miles total for the tax year. (August listed the missing filter as
  Low. It's the core filing workflow, so it's raised here.)

### N6. After deep sleep, an SNTP "success" can freeze a drifted clock for the whole day

ESP-IDF keeps system time across deep sleep using the RTC slow clock (an
internal RC oscillator, which drifts noticeably with temperature). On wake,
`trySntp()` (`:638-646`) calls `getLocalTime(&tmv, 5000)`. That returns true
as soon as the year looks valid, **which the carried-over time already
does**, so `gClockSet = true` before SNTP has synced. The WiFi is then shut
off, and because `loop()` only sets the clock from GPS when `!gClockSet`
(`:860`), **GPS never corrects it**. Every timestamp for that boot is off by
the sleep drift.

This only happens when the device wakes at home with un-uploaded trips. It
moves times, not miles. **Fix:** check `sntp_get_sync_status()` instead of
`getLocalTime`, and let GPS time always take over (resync from GPS
periodically, not just once).

## Low

- **N7. UFW doesn't protect the Docker ports.** Docker publishes ports through
  its own iptables chain, ahead of UFW's rules, so the `ufw allow from
  192.168.1.0/24` lines in `DEPLOY_DEBIAN.md` Step 7 don't restrict anything.
  The "extra hardening" bind address (`"192.168.1.10:8090:8090"`) is the
  control that actually works. Make it the main instruction.
- **N8. `end_time` and duration include the 3-minute cooldown.** Every trip
  reads 3 minutes longer and ends 3 minutes late, and the average speed is
  understated. Fixed with N1's tail trim.
- **N9. Deep sleep can unmount the FS under an in-flight upload.**
  `deepSleepForVbus()` calls `LittleFS.end()` (`:571`) while the net task on
  core 0 may still be reading the upload file through `LockedFileStream`.
  The worst case is a crash and reboot instead of sleep. The trip file is
  safe. Stop the net task and WiFi before unmounting.
- **N10. IRQ clear/disable order before sleep.** `clearIrqStatus()` runs
  *before* `disableIRQ(ALL)` (`:574-575`). An event in between holds the
  line low, so the board wakes immediately and reboots. Disable first, then
  clear.
- **N11. The compose comment gives the wrong reason** (`docker-compose.yml`,
  `env_file`). Checked with Compose v5.3.1: unquoted `env_file` values **are**
  interpolated (`scrypt:…$abc$def` → `scrypt:…`). The single quotes in
  `viewer.env` are what protect the hash, and the startup check catches the
  unquoted case. The instructions are right. Only the explanation needs
  correcting.
- **N12. `gpx.js` builds waypoint popups from raw GPX `name`/`desc` HTML**
  (`static/gpx.js:446`). This would be stored XSS, but only if someone holding
  the ingest token uploads a GPX with `<wpt>` elements, and the device never
  emits any. Escape the values or strip `<wpt>` on ingest.
- **N13. The backup recipe tars a live SQLite file** (`DEPLOY_DEBIAN.md`
  Step 10). It can capture a torn write. Use
  `sqlite3 annotations.db ".backup …"`, or stop the viewer first, and
  schedule it rather than relying on "before each filing".
- **N14. Docs are stale.** The sketch header and both READMEs still say "core
  3.3.9", and CLAUDE.md's status section predates the August audit.

## Verified sound (this pass)

- The `LockedFileStream` proxy is actually used. `Stream::readBytes` is
  `virtual` in core 3.3.11 (`Stream.h:108`), and `HTTPClient::sendRequest`
  drives it chunk by chunk.
- The rest of the August "verified sound" list still holds: path-traversal
  guard, Jinja autoescape, CSRF on every authenticated POST, the SQLite-backed
  lockout, session regeneration on login, non-root containers, the read-only
  data mount, `findLastTrkptEnd`'s carry logic, rollover-safe `millis()`
  arithmetic, `timegmUtc`, and FS-lock nesting (no re-entrant take).
- Server end-to-end happy path: `sample.gpx` → 200, 0.295 mi, bucketed
  `2026-04/`. Login, list, annotate and both exports work.
- XPowersLib disables the TS pin itself, so charging isn't blocked by a
  missing thermistor (that's the cause of N4, but it isn't a charging failure).

# Part 3 — Suggested order

The August order stands, with the new items slotted in:

1. **B3** — one function; stops the permanent retry loop.
2. **F3 + F4** — open-failure path and write checks.
3. **F2 + GPS config** — one UBX block at boot: disable GLL/GSA/GSV/VTG, keep
   1 Hz, and set the automotive dynamic model (helps N1). Then re-size
   `gArmBuf` and `gPend`.
4. **F1** — slim format (**keep `hdop`**), free-space guard, and settle on one
   partition (the brief's custom 2.38 MB) across all three docs.
5. **F6 + F10** — before the road test, or the road test produces split
   trips and stuck uploads.
6. **N1 + N2** — server distance: speed/hdop gate, bridge gaps, trim the
   cooldown tail, plus a re-summarize script. Can follow the road test, but
   **must** be done before any totals are trusted.
7. **N5** export additions, then **B1, B4, B5**, **N6**, the remaining
   mediums, and the Low list.

# Bench results (2026-10-05, board on USB)

- The board was running an older Stage 4 build (from before the June review) on
  the default partition table. Its LittleFS image was read out first; it held
  an empty `/trips` and no trackpoint data at all, so nothing was lost to the
  reformat.
- Current build flashed: PMU OK, VBUS present, the new 2.375 MB partition mounts,
  and **the M8N ACKs all five UBX messages** ("GPS configured: RMC+GGA only,
  automotive model"). The GPS clock is set indoors.
- **N3, measured with a probe sketch** (counting GPS UART bytes over 3 s per
  state):

  | State | GPS output |
  |---|---|
  | ALDO3 on, ALDO4 on | 439 B |
  | ALDO4 off | 444 B: unaffected |
  | ALDO3 off | **0 B** |

  The as-found rails were DC1, ALDO1, ALDO2, ALDO3 and BLDO1 on, with
  button-battery charge (VBACKUP) **off**. About 146 B/s matches RMC+GGA only,
  which independently confirms the UBX config took effect.
- `E (…) gpio: gpio_pullup_en(85): GPIO number error` at boot is the core's UART
  driver trying to pull up GPIO34 (input-only). It's cosmetic.
- **N4, die temperature vs charging** (a probe sketch, room 78 °F / 25.6 °C,
  battery full at 4.18 V, charger set to 300 mA / 4.2 V):

  | State | Die |
  |---|---|
  | Idle / charge done | 34.7–35.0 °C (≈ +9 °C over the room) |
  | Charging disabled | 34.6–34.75 °C |
  | A 30 s top-up charge (CV) | 34.65 → 36.95 °C and still rising; back down ~45 s after it ended |

  The guard's thresholds use that 9 °C offset, with a 7 °C pause/resume gap
  for the self-heating. After reflashing, the board logs "Charge guard: die
  34.3 C (battery ~25 C), charging on", which agrees with the room. The offset
  was measured bare on a desk; inside the enclosure it is likely larger,
  which errs toward pausing early.
- Still needs the car or a meter: deep-sleep current, hot-start time after
  sleep, F11 stack high-water mark during a real upload, and the road test.
