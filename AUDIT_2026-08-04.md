Full audit of the backend (`server/mileage-ingest`, `server/mileage-viewer`,
compose/Dockerfiles) and the Stage 4 firmware sketch
(`firmware/04_trip_logger/04_trip_logger.ino`).

**Fix status: B2 only.** This document is otherwise the finding list only.
B2 (timezone) was resolved and implemented on 2026-08-04 — see that

## Method

# Part 1 — Backend

## High

### B1. XLSX export is vulnerable to formula injection — and the comment says it isn't

`mileage-viewer/app.py:726` `_csv_safe()` guards only the CSV path. The
comment at line 731 claims *"XLSX export is unaffected (openpyxl writes
strings as literal strings)."* That is false. openpyxl's `Cell._bind_value`
sets `TYPE_FORMULA` on any string starting with `=`.

Reproduced — annotated a trip with the note `=1+1`, exported both formats:

```
CSV:  '=1+1               data_type='s'   (neutralized)
XLSX: =1+1                data_type='f'   (live formula)
```

Low exploitability (you are the only one entering notes), but the XLSX is the
IRS artifact. A note like `=-Client visit` renders as `#NAME?` in the
exported record.

**Fix:** apply `_csv_safe` to the XLSX path too, or set
`cell.data_type = 's'` explicitly on text columns.

### B2. All times display and export in UTC — dates can be wrong by a day

`fmt_date()` (line 384) parses the ISO string and calls `strftime` directly on
the timezone-aware datetime. `TZ=America/Los_Angeles` in `docker-compose.yml`
affects log lines, not this.

A 6:00 pm PDT drive is stored `2026-04-15T01:00Z`, and the viewer's Date
column shows **2026-04-15**. Same for `start_time` / `end_time` in both
exports. Month bucketing puts a Dec 31 evening trip in `2027-01/`.

~~**Decision (2026-08-04): keep everything in UTC**, reduced to a labeling
fix.~~ **Superseded the same day — see below.**

**RESOLVED (2026-08-04): display and export in Pacific Time
(`America/Los_Angeles`). Storage stays UTC. Implemented.**

UTC display was reconsidered: this artifact is an IRS mileage record, and
the day a trip is filed under has to be the day it was actually driven.
Labeling the column "UTC" would have made the offset visible but left the
reader doing the arithmetic on every row.

What was implemented:

- `DISPLAY_TZ = ZoneInfo("America/Los_Angeles")` in **both** services,
  overridable via a `DISPLAY_TZ` env var, wired in `docker-compose.yml`.
  A named IANA zone, never a fixed offset — Pacific observes DST, so
  `-08:00` would be an hour wrong from March to November.
- `fmt_date()` renders local time with a `%Z` suffix, so rows read
  `2026-04-14 18:00 PDT` — self-labeling, and correct across the DST
  boundary without a hardcoded string.
- Export `start_time`/`end_time` are now local ISO-8601 **with offset**
  (`2026-04-14T18:00:00-07:00`), so the exact instant is still
  recoverable from the exported record.
- Month bucketing moved to local in the ingest service, so the folder and
  the displayed date agree. A 6pm PST Dec 31 drive now files under
  `2026-12/` instead of `2027-01/` — the tax-year boundary was the whole
  point.
- Timestamps *inside* the stored files are untouched: the raw GPX is still
  byte-for-byte as uploaded, and summary `start_time`/`end_time` are still
  UTC. Only presentation and the folder name changed.
- `tzdata` added to both `requirements.txt`. Both services raise at import
  if the zone database is missing rather than silently falling back to
  UTC, which would reintroduce this bug invisibly.

Verified in the built containers: 21 viewer checks (DST both directions,
the day-shift case, naive input, CSV/XLSX export) and 11 ingest checks
(local bucketing at both a month and a year boundary, UTC preserved in
storage). All pass.

## Medium

### B3. A GPX timestamp without a timezone crashes the ingest (500)

`_parse_iso` (`mileage-ingest/app.py:130`) returns a naive datetime for
`<time>2026-04-14T14:30:15</time>` (no `Z`). `summarize()` then does
`min(times)` at line 245:

```
TypeError: can't compare offset-naive and offset-aware datetimes
```

Reproduced: returns 500, trip lost. The firmware always emits `Z`, so this is
a robustness gap rather than a live failure — but it is an unhandled crash on
the only code path that matters, and it interacts badly with firmware F6
(retried forever).

**Fix:** normalize to UTC-aware in `_parse_iso` — assume UTC when no offset is
present.

### B4. `hmac.compare_digest` raises TypeError on non-ASCII → 500

Four unauthenticated-reachable call sites:

| File | Line | Context |
|---|---|---|
| `mileage-ingest/app.py` | 371 | bearer token |
| `mileage-viewer/app.py` | 634 | username |
| `mileage-viewer/app.py` | 314 | CSRF (global hook) |
| `mileage-viewer/app.py` | 618 | CSRF (login view) |

Reproduced both: `Authorization: Bearer café` 500s the ingest;
`username=phíl` 500s the viewer login. Should be a clean 401.

**Fix:** `.encode()` both sides before comparing, or reject non-ASCII early.

### B5. A GPX with zero track points is accepted

Reproduced: `<gpx></gpx>` returns `200 accepted` and writes a phantom 0-mile
trip, bucketed under the current month with a content-hash id
(`untimed-75829de272da`). If the firmware ever finalizes an empty trip — see
F3 — it lands in the mileage log.

**Fix:** 400 when `num_points == 0`.

## Low

- `_atomic_write_bytes` uses a fixed `<id>.tmp`; two gunicorn workers
  uploading the same trip id can interleave. Use a unique suffix.
- No `fsync` before rename — atomic for readers, not durable across power loss.
- 413 returns HTML, not JSON (reproduced). Cosmetic; the firmware only checks
  status codes.
- `duration_seconds` uses a falsy check (line 290), so a 0-second trip stores
  `None` and renders `—`.
- Timestamp-derived `trip_id` in the JSON (`...+00-00`) doesn't match the
  filename stem (`..._00-00`), so the export's `trip_id` column doesn't match
  the file on disk.
- `_record_failure` does read-then-write outside one transaction; two workers
  can undercount lockout failures.
- A logged-in POST to an unknown path returns 400 (CSRF hook) instead of 404.
- `trip_view` loads JSON without try/except; `load_trips` does. A corrupt file
  500s the detail page.
- `ET.fromstring` is entity-expansion-prone. Behind auth and a 4 MB cap, so
  low — `defusedxml` is a two-line fix.
- `_csv_safe` misses a leading `-`, which Excel also treats as a formula.
- No date-range filter on export — every year in one file.
- Changing `VIEWER_PASSWORD_HASH` does not invalidate live sessions.

## Verified sound

Path traversal is genuinely blocked (strict regex plus a `resolve()` check).
Jinja autoescape is on for `render_template_string` (Flask 3.x returns True
for a `None` template name). CSRF covers every authenticated POST including
logout. Lockout state lives in SQLite, correctly, because of the two workers.
Session regenerates on login. Containers run non-root; the viewer's data mount
is read-only. `.gitignore` is correct — `firmware/04_trip_logger/secrets.h`
**is** ignored via the nested bare `secrets.h` pattern, confirmed with
`git check-ignore`, and it is untracked. `DEPLOY_DEBIAN.md` Step 3 already
covers the bind-mount ownership trap that would otherwise 500 every upload.

**Nothing in Part 1 blocks deployment.**

# Part 2 — Firmware (`04_trip_logger.ino`)

## High

### F1. The device runs out of flash in about two hours of driving

`appendTrkpt` emits **281 bytes per point** (measured against the sample.gpx
field set). Against the brief's no-OTA partition (`0x260000` = 2.38 MB):

| Rate | Capacity | Driving time before full |
|---|---|---|
| 1 Hz | 8,863 points | **2.5 hours** |
| 2 Hz (see F2) | 8,863 points | **1.2 hours** |

The Stage 4 brief's *"roughly 13 days of dense 1 Hz logging"* assumed
~100 B/s. The sketch writes 2.8× that.

There is **no free-space check anywhere** — `grep` for
`usedBytes|totalBytes|rotate` returns nothing — despite the brief explicitly
calling for it: *"joltwallet/esp_littlefs #183 (100%-full partition triggers
divide-by-zero — pre-check `usedBytes()/totalBytes()` and rotate before
full)."*

One long road trip, or a week away from home WiFi, fills the partition.

**Decision (2026-08-04): slim the format + add a free-space guard.**
Drop `sat` / `hdop` / `course`, use `%.6f` for lat/lon, shorten fields —
roughly 281 → ~110 B/point. Add a `usedBytes()/totalBytes()` pre-check that
refuses to start a new trip below a threshold, and logs loudly. That gets
capacity back near the brief's original estimate. Rotation and decimation
deliberately not chosen — neither should silently discard real mileage.

### F2. Every position is logged twice

`loop()` gates on `gps.location.isUpdated()` (line 866). TinyGPSPlus updates
`location` from **both GGA and RMC**, and the M8N emits both once per epoch.
The sketch never sends any UBX configuration to the GPS — `GPS_TX_PIN` is
defined but nothing is ever written to `GPSSerial`.

Result: two trkpts per second at identical coordinates, with the
GGA-triggered one carrying the *previous* epoch's speed.

Beyond doubling F1, this invalidates two sizing assumptions stated in the
code's own comments:

- `gArmBuf[16]` — comment (line 139) says *"a 10 s arm window is 10-11 fixes;
  16 slots is comfortable headroom."* At 2 Hz it is 20 fixes, so the buffer
  overflows and the first ~2 s of every trip is silently dropped, along with
  the true `gTripT0`.
- `gPend[90]` — comment (line 124) says ~90 s of cold-start coverage. It is 45 s.

**Fix:** send UBX-CFG-MSG at boot to disable GLL/GSA/GSV/VTG and confirm the
1 Hz rate, or gate the FSM on RMC only. Then re-check both buffer sizes.

### F3. A failed file open produces invalid GPX forever

In `beginTrip` (line 310), if `LittleFS.open(..., FILE_WRITE)` fails,
`gTripPath` is already set and the function falls through — the caller sets
`gState = ACTIVE` regardless (line 425). Every subsequent
`writeOrBufferTrkpt` opens `FILE_APPEND`, which *creates* the file, **without
the prologue**. `endTrip` appends the epilogue, yielding
`<trkpt>…</trkseg></trk></gpx>` — not valid XML.

The server returns 400 and, per F6, the device retries every 30 s forever.

`endTrip` has the same shape: `FILE_APPEND` on a nonexistent file creates one
containing only the epilogue. On a power-loss finalize
(`discardIfMicro=false`) that file is *kept* and uploaded.

**Fix:** on open failure, clear `gTripPath` and return to IDLE.

### F4. No write result is ever checked

All 13 `f.print` / `f.printf` / `out.write` calls discard their return value
(lines 258–269, 312, 376, 524–528). On a full filesystem (F1) points vanish
with no error, no serial output, and no indication until miles go missing.

## Medium

### F5. `LittleFS.begin(true)` formats on mount failure

Line 839. Destroys every un-uploaded trip. The brief recommends it for
self-healing, but that trade is wrong for the one thing on this device that
cannot be regenerated — a transient mount error becomes indistinguishable
from a wipe.

**Fix:** try `begin(false)` first; only format after an explicit second
attempt, and log it unmistakably.

### F6. Upload has no permanent-failure path

`uploadFile` line 716: `ok = (code == 200)`. A 400 (malformed GPX) is retried
identically to a 500 or a network error — every 30 s, indefinitely, never
quarantined.

**Fix:** on a 4xx, rename to `.bad` so it stops retrying but survives for
inspection.

### F7. `fsckAllTrips` mutates the directory while iterating it

`repairIfNeeded` creates `.fix`, removes, and renames inside the open
`openNextFile()` walk (lines 536–549). Advancing one entry ahead does not
cover that. `uploadPending()` already does this correctly — snapshot the names
under the lock, then act. `fsck` should match.

### F8. Interrupted repairs leave orphaned `.fix` files

Never cleaned up, and never uploaded (they don't end in `.gpx`). They just
consume the flash from F1.

### F9. `repairIfNeeded` deletes the original before validating the replacement

Line 531 `remove` → 532 `rename`. Power loss in that window loses the trip
outright, and the `out.write` result isn't checked, so a truncated `.fix` can
replace a good file.

### F10. VBUS-removed has no debounce

Line 592 finalizes the trip on the first VBUS-remove IRQ. Engine cranking
browns out the USB port on plenty of cars, so one drive becomes two trips —
and each half may then fall under `MIN_TRIP_METERS` and be discarded. A 5–10 s
persistence check before acting would fix it.

This is the class of bug that only surfaces on the road test.

### F11. Net task stack is 8192

Line 848. The brief's own skeleton specifies 12288 and states *"stack sizing
is load-bearing… 12,288 bytes minimum in practice."* The sketch uses plain
`WiFiClient`, not `WiFiClientSecure`, so 8 KB is defensible — but it is an
unmeasured deviation, and an overflow here crashes mid-trip.

**Fix:** measure with `uxTaskGetStackHighWaterMark(NULL)` during the shakedown
and size from data.

## Low

- No `X-Trip-Id` header sent, so the server falls back to the timestamp id and
  every file lands as `2026-04-14T14-30-00_00-00.gpx`.
- No `http.setTimeout()` / `setConnectTimeout()` — the 5 s default against a
  several-hundred-KB body over WiFi.
- `homeApInRange()` runs a full ~2 s scan every 30 s forever when the server is
  unreachable; no backoff, no `WiFi.scanDelete()`.
- Device-side `gTripMeters` counts distance across `<trkseg>` gaps; the server
  deliberately does not. Only affects the micro-trip discard decision, not
  reported mileage — but the two numbers will never agree.
- `e.name()` returning a basename is core-3.x behavior; on core 2.x this builds
  `/trips//trips/t000001.gpx`. Fine as pinned — worth a comment.
- `gClockSet` is written from both cores non-atomically (benign);
  `gTripPath[0] = 0` is set outside the FS lock in `endTrip` (benign).
- `%.7f` on lat/lon is ~1 cm precision; `%.6f` saves 2 B/point — folded into
  the F1 fix.
- `xSemaphoreCreateMutex()` return unchecked.
- The brief notes the Meshtastic-confirmed V1.2 mapping is **ALDO3 = GPS**, not
  ALDO4. Stages 2–3 proved ALDO4 works on this unit, so keep it — but
  `deepSleepForVbus` disables ALDO4 only, so if both rails are live the GPS may
  not fully power down in sleep. One meter check during the shakedown settles it.

## Verified sound

The concurrency design holds up. Every `FS_LOCK` path was traced for nesting —
the mutex is non-recursive and there is no re-entrant take anywhere, so no
deadlock exists. `LockedFileStream` is the right fix for the upload/GPS
contention, and ESP32 `HTTPClient::sendRequest(const char*, Stream*, size_t)`
does drive it through `readBytes`. `findLastTrkptEnd`'s carry-buffer
arithmetic is correct, including a token spanning a read boundary and the
`region[272]` sizing (max 7 + 256 = 263). All `millis()` comparisons use the
rollover-safe unsigned-difference form. `timegmUtc` is a correct days-from-civil
implementation, and avoiding `mktime` is the right call. The FINALIZING-in-same-pass
fix, the ARMING capture, and the stationary jitter gate from the June review all
read correctly.

# Part 3 — Cross-cutting

Three pairs interact worse than either half alone:

| Firmware | Backend | Combined effect |
|---|---|---|
| F3 emits invalid GPX | 400 | F6 retries it every 30 s forever |
| Naive-datetime GPX | B3 → 500 | Retried forever, trip never lands |
| F1 flash fills silently | — | Trips lost with no signal on either side |

**B3 is worth fixing regardless of scope** — it turns a recoverable
device-side glitch into a permanent upload loop.
